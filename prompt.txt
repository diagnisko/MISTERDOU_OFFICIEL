PROJET : PLATEFORME DE VENTE DE COMPTES eFOOTBALL

1. OBJECTIF DU PROJET

Je veux développer une plateforme web moderne, rapide, sécurisée et évolutive permettant d’acheter et de vendre des comptes eFootball.

La plateforme doit gérer trois types d’utilisateurs :

1. Client
2. Vendeur
3. Administrateur

L’objectif est de créer d’abord une excellente plateforme web, avec une architecture suffisamment propre et évolutive pour permettre ensuite de développer une application mobile iOS et Android utilisant le même backend et les mêmes API.

⸻

2. CHOIX TECHNOLOGIQUE

Avant de commencer le développement, choisis une stack moderne privilégiant :

* vitesse d’exécution ;
* rapidité de chargement ;
* bonnes performances sur mobile ;
* sécurité ;
* évolutivité ;
* facilité de maintenance ;
* possibilité de créer plus tard une application mobile avec les mêmes API.

Propose une architecture moderne avec, par exemple :

Frontend

Une technologie performante permettant une excellente expérience utilisateur.

Backend

Une technologie rapide et adaptée à une plateforme transactionnelle.

Base de données

Une base de données relationnelle robuste permettant de gérer :

* utilisateurs ;
* comptes eFootball ;
* commandes ;
* paiements ;
* échéances ;
* vendeurs ;
* commissions ;
* promotions ;
* vérifications KYC ;
* transactions ;
* notifications ;
* historique des actions.

Stockage

Les documents d’identité, photos et autres fichiers sensibles doivent être stockés de manière sécurisée et ne doivent jamais être publiquement accessibles.

Architecture

Construire le projet avec une séparation claire :

Frontend → API sécurisée → Backend → Base de données / stockage / paiement.

Prévoir dès le départ une API propre afin de pouvoir réutiliser le backend pour l’application mobile future.

⸻

3. TYPES DE COMPTES

3.1 CLIENT

Un utilisateur peut créer un compte client :

* avec Google ;
* ou avec une inscription classique.

Lors de son inscription, son compte doit rester limité tant que son identité n’a pas été vérifiée.

⸻

4. VÉRIFICATION D’IDENTITÉ OBLIGATOIRE

Avant de pouvoir acheter un compte eFootball, le client doit obligatoirement être vérifié.

Le client doit fournir :

* recto de sa pièce d’identité ;
* verso de sa pièce d’identité ;
* OU passeport ;
* photo de son visage.

Le système doit avoir plusieurs statuts :

* Non vérifié
* Vérification en attente
* Vérifié
* Refusé

Un client non vérifié ne doit pas pouvoir finaliser l’achat d’un compte.

L’administrateur doit pouvoir :

* consulter les demandes de vérification ;
* accepter une vérification ;
* refuser une vérification ;
* demander une nouvelle soumission ;
* consulter l’historique de vérification;
consulter les clients et vendeur et leur informations
ajouter des manager et leur permission .

Les documents sensibles ne doivent jamais être visibles publiquement.

⸻

5. COMPTE VENDEUR

Un client vérifié peut demander à devenir vendeur.

Pour devenir vendeur, il doit payer des frais d’inscription de :

1 000 FCFA

Ces frais sont définitifs et ne constituent pas un abonnement mensuel.

Prévoir éventuellement une configuration administrateur permettant de modifier ce montant.

Une fois le paiement confirmé :

* le compte client obtient le statut vendeur ;
* le vendeur peut publier des comptes eFootball ;
* le vendeur peut gérer ses propres annonces ;
* le vendeur peut suivre ses ventes et ses revenus donc les compte vendeur doit avoir un tableau  de bord.

Un vendeur reste également un utilisateur client et peut donc acheter des comptes.

⸻

6. VENTE DES COMPTES PAR LES VENDEURS

Les comptes publiés par les vendeurs sont vendus en un seul paiement.

Il n’y a pas de paiement en plusieurs fois pour les produits des vendeurs.

Lorsqu’un vendeur crée une annonce, il doit renseigner au minimum :

* nom/titre du compte ;
* description ;
* prix ;
* puissaner de l’équipe ;
* nombre de pièces ;
* division ;
* informations complémentaires ;
* captures d’écran du compte ;
* e-mail du compte eFootball ;
* mot de passe du compte eFootball.

IMPORTANT — DONNÉES CONFIDENTIELLES

L’e-mail et le mot de passe du compte eFootball sont des informations extrêmement sensibles.

Ils ne doivent :

* jamais apparaître dans la page publique du produit ;
* jamais apparaître dans les résultats de recherche ;
* jamais être visibles par les autres utilisateurs ;
* jamais être envoyés au frontend inutilement.

Ils doivent être stockés de manière sécurisée et chiffrée.

Seuls les utilisateurs autorisés doivent pouvoir accéder à ces informations selon les règles définies par l’administrateur.

⸻

7. COMMISSION SUR LES VENTES VENDEURS

Lorsqu’un compte est vendu par un vendeur :

15 % du montant de la vente revient à l’administrateur.

Le reste revient au vendeur, sous réserve des éventuels frais de paiement.

Exemple :

Compte vendu à 20 000 FCFA.

Commission administrateur :

20 000 × 15 % = 3 000 FCFA

Montant vendeur :

17 000 FCFA

Le système doit automatiquement calculer :

* prix de vente ;
* commission ;
* montant vendeur ;
* frais éventuels ;
* montant net.

Chaque transaction doit être enregistrée dans l’historique financier.

⸻

8. VENTE DES COMPTES DE L’ADMINISTRATEUR

L’administrateur possède également ses propres comptes eFootball.

Contrairement aux vendeurs, l’administrateur peut proposer ses comptes avec un paiement en plusieurs fois.

Lors de la création du produit, l’administrateur doit pouvoir définir :

* prix total ;
* montant de l’apport initial ;
* nombre de mensualités.

Le nombre de mensualités doit être configurable.

Maximum :

8 mois.

Exemple :

Prix : 80 000 FCFA

Apport initial : 20 000 FCFA

Reste : 60 000 FCFA

Nombre de mensualités : 6

Le système calcule automatiquement :

60 000 / 6 = 10 000 FCFA par mois.

Prévoir également la gestion des arrondis afin qu’il n’y ait jamais de différence entre le total payé et le prix réel du produit.

⸻

9. SYSTÈME DE PAIEMENT EN PLUSIEURS FOIS

Pour les produits de l’administrateur, le système doit créer automatiquement un échéancier.

Exemple :

* Paiement initial : 20 000 FCFA
* Mois 1 : 10 000 FCFA
* Mois 2 : 10 000 FCFA
* Mois 3 : 10 000 FCFA
* etc.

Le système doit suivre :

* montant payé ;
* montant restant ;
* prochaines échéances ;
* échéances payées ;
* échéances en retard ;
* date de chaque paiement ;
* statut de chaque paiement.

Le client doit pouvoir voir clairement son échéancier depuis son espace personnel.

13. PRODUITS MIS EN AVANT

Les vendeurs doivent pouvoir payer pour mettre leurs produits en avant.

Tarification prévue :

200 FCFA par jour.

Le vendeur choisit :

* le produit ;
* le nombre de jours ;
* paie le montant correspondant.

Exemple :

1 jour = 200 FCFA

5 jours = 1 000 FCFA

10 jours = 2 000 FCFA

30 jours = 6 000 FCFA

Le système doit calculer automatiquement le prix.

Après paiement confirmé :

* le produit devient “mis en avant” ;
* il apparaît dans les emplacements prévus ;
* la durée commence ;
* le système désactive automatiquement la mise en avant à expiration.

L’administrateur doit pouvoir contrôler les produits mis en avant.

⸻

14. PAIEMENTS

Tous les paiements de la plateforme doivent passer par PayTech.

Prévoir les moyens de paiement disponibles sur PayTech, notamment les moyens compatibles avec le marché ciblé.

Lorsqu’un utilisateur clique sur “Payer”, il doit pouvoir choisir le moyen de paiement disponible via PayTech.

Tous les paiements doivent être confirmés côté serveur.

IMPORTANT :

Ne jamais considérer simplement une redirection frontend comme preuve qu’un paiement est réussi.

Utiliser les mécanismes de confirmation/webhook de PayTech afin de vérifier réellement le statut de la transaction.

Chaque paiement doit avoir :

* identifiant unique ;
* utilisateur ;
* commande ;
* montant ;
* type de paiement ;
* fournisseur ;
* statut ;
* date ;
* référence ;
* historique.

Statuts possibles :

* pending
* processing
* success
* failed
* cancelled
* refunded

15. PROCESSUS APRÈS ACHAT

Lorsqu’un client achète un compte :

1. Le paiement est confirmé.
2. La commande passe à “Payée”.
3. Le système récupère les informations privées du compte.
4. Le client reçoit les informations nécessaires pour accéder au compte.
5. Les informations sensibles doivent être transmises par un mécanisme sécurisé.

L’e-mail et le mot de passe du compte ne doivent jamais être affichés dans le catalogue avant l’achat.

⸻

16. CODE DE VÉRIFICATION / AIDE À LA CONNEXION

Si eFootball demande un code de vérification lors de la connexion au compte acheté, le client doit pouvoir demander de l’aide depuis sa commande.

Créer un système de support permettant de suivre cette procédure.

Acteurs pouvant aider :

* administrateur ;
* membre du personnel autorisé.

Le client doit pouvoir créer une demande :

“J’ai besoin du code de vérification.”

Le personnel autorisé traite ensuite la demande.

Prévoir un système de statut :

* demande créée ;
* en attente ;
* en cours de traitement ;
* code fourni / procédure terminée ;
* terminé.

Toutes les actions doivent être enregistrées dans un journal d’activité.

⸻

17. LIBÉRATION DES REVENUS VENDEURS

L’argent d’une vente vendeur ne doit pas être immédiatement considéré comme disponible si la plateforme impose une période de vérification ou de sécurisation.

Créer un système de solde :

Solde en attente

Argent provenant de ventes encore en cours de traitement.

Solde disponible

Argent pouvant être retiré par le vendeur.

L’administrateur doit pouvoir contrôler le moment où les fonds deviennent disponibles conformément aux règles de la plateforme.

Avant qu’un retrait soit possible, vérifier que toutes les informations nécessaires du vendeur sont correctement renseignées.

21. RÔLES ET PERMISSIONS

Ne pas donner tous les droits directement à tous les utilisateurs.

Créer un véritable système RBAC (Role-Based Access Control).

Exemple :

CLIENT

Accès uniquement à ses propres données.

VENDEUR

Accès :

* à ses produits ;
* ses commandes ;
* ses revenus ;
* ses informations personnelles.

Il ne doit jamais pouvoir accéder aux données des autres vendeurs.

STAFF / MODÉRATEUR

Accès limité aux fonctions nécessaires.

ADMINISTRATEUR

Accès complet.

Toutes les permissions doivent être contrôlées côté backend.

Ne jamais faire confiance uniquement aux permissions du frontend.

* logs de sécurité ;

* variables d’environnement ;

33. PAIEMENTS ET WEBHOOKS

Créer une architecture robuste pour PayTech.

Lorsqu’un paiement est effectué :

1. Créer une transaction interne.
2. Envoyer la demande de paiement à PayTech.
3. Attendre la confirmation.
4. Recevoir le webhook.
5. Vérifier l’authenticité du webhook.
6. Vérifier le montant et la référence.
7. Mettre à jour la transaction.
8. Mettre à jour la commande.
9. Générer les actions correspondantes.

Ne jamais créditer un vendeur simplement parce que le frontend indique “paiement réussi”.

40. OBJECTIF FINAL

Je veux obtenir une plateforme eFootball qui soit :

rapide + moderne + sécurisée + évolutive + professionnelle.

Elle doit pouvoir commencer avec peu d’utilisateurs mais être conçue pour évoluer progressivement vers une plateforme avec beaucoup plus d’utilisateurs et de transactions.

1. sécurité ;
2. fiabilité des paiements ;
3. protection des données sensibles ;
4. performance ;

6. évolutivité.

41. SYSTÈME DE MESSAGERIE

La plateforme doit intégrer un système de messagerie interne permettant aux utilisateurs autorisés de communiquer directement.

Client ↔ Administrateur

Un client doit pouvoir envoyer un message directement à l’administrateur.

Le fonctionnement doit être similaire à une conversation :

* le client ouvre une conversation ;
* il écrit un message ;
* l’administrateur reçoit une notification ;
* l’administrateur peut répondre ;
* le client reçoit une notification de réponse.

Chaque conversation doit avoir :

* un identifiant ;
* un expéditeur ;
* un destinataire ;
* des messages ;
* une date ;
* une heure ;
* un statut lu/non lu ;
* éventuellement des pièces jointes si cette fonctionnalité est activée.

⸻

42. ADMINISTRATEUR ↔ VENDEUR

L’administrateur doit également pouvoir contacter directement un vendeur.

L’administrateur peut :

* démarrer une conversation avec un vendeur ;
* envoyer des messages ;
* répondre aux messages ;
* envoyer des informations concernant une vente ;
* demander des informations supplémentaires ;
* informer le vendeur d’un problème ;
* envoyer des notifications importantes.

Le vendeur doit recevoir une notification lorsqu’un administrateur lui envoie un message.

⸻

43. SÉPARATION DES CONVERSATIONS

IMPORTANT :

Les clients ne doivent jamais pouvoir discuter directement avec les vendeurs.

Un client peut uniquement communiquer avec :

* l’administrateur ;
* éventuellement un membre du personnel autorisé.

Un vendeur peut communiquer avec :

* l’administrateur ;
* éventuellement un membre du personnel autorisé.

Il ne doit jamais être possible pour un client de découvrir ou contacter directement un vendeur via le système de messagerie.

46. NOTIFICATIONS PUSH

Préparer l’architecture pour les notifications push.

L’objectif est qu’un utilisateur puisse recevoir une alerte même lorsqu’il n’est pas actuellement sur la plateforme.

Exemple :

Un administrateur envoie un message à un vendeur.

Le vendeur reçoit :

🔔 Nouveau message

Vous avez reçu un nouveau message de l’administration.

En cliquant sur la notification, l’utilisateur est redirigé directement vers la conversation concernée.

Pour l’application mobile future, prévoir une intégration avec le système de notifications push adapté à Android et iOS.

49. LOCALISATION

2. demander le consentement de l’utilisateur ;

4. récupérer la position uniquement après autorisation ;
5. enregistrer les coordonnées nécessaires ;
6. éventuellement convertir les coordonnées en adresse approximative ou zone géographique.

La localisation doit être collectée uniquement lorsque cela est nécessaire au processus prévu et conformément au consentement de l’utilisateur.

55. PROTECTION DES DOCUMENTS D’IDENTITÉ

Les pièces d’identité ne doivent JAMAIS être placées dans un dossier public accessible directement par URL.

Utiliser un stockage privé.

L’accès doit fonctionner de cette manière :

Administrateur authentifié
↓
Backend vérifie les permissions
↓
Backend génère un accès temporaire et sécurisé
↓
Document affiché à l’administrateur autorisé

Les documents doivent être protégés contre :

* accès public ;
* enumeration des fichiers ;
* téléchargement non autorisé ;
* accès par un autre utilisateur ;
* modification non autorisée.

56. ACCÈS AUX DONNÉES SENSIBLES

L’accès aux données sensibles doit être soumis à des permissions strictes.

Un client ne peut consulter que ses propres informations.

Un vendeur ne peut consulter que ses propres informations.

Un administrateur autorisé peut consulter les informations nécessaires à la gestion de la plateforme.

Chaque consultation importante d’un document sensible doit pouvoir être enregistrée dans l’AuditLog.

Exemple :

Administrateur X a consulté le document d’identité du vendeur Y.

Date et heure enregistrées.

63. RÈGLES DE CONFIDENTIALITÉ

Les informations personnelles et documents d’identité doivent être traités comme des données hautement sensibles.

Le système doit appliquer le principe du moindre privilège.

Chaque utilisateur ne doit avoir accès qu’aux données dont il a réellement besoin.

La localisation ne doit pas être collectée ou utilisée en arrière-plan sans consentement approprié.

Les données doivent avoir une politique de conservation définie et respecter les obligations légales applicables aux utilisateurs et au pays où le service est exploité.

65. IMPORTANT — PRINCIPES À RESPECTER

Ne jamais :

* exposer publiquement les pièces d’identité ;
* exposer publiquement les mots de passe eFootball ;
* permettre à un client de contacter directement un vendeur ;
* permettre à un vendeur de consulter les données d’un autre vendeur ;
* faire confiance au frontend pour les permissions ;
* considérer une redirection PayTech comme une confirmation de paiement ;
* stocker les secrets dans le code ;
* stocker les documents sensibles dans un stockage public ;
* suivre la localisation en permanence sans nécessité et consentement approprié.

Le système doit être conçu avec une approche security-by-design et privacy-by-design.
